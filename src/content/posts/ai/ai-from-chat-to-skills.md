这篇不讲怎么安装。Claude Code、OpenClaw、Ollama 的安装笔记已经有了，文末有链接。这里只记我自己用 AI 的顺序：先会聊天，再让它进项目，然后把习惯写成规则，最后把重复的事收成技能。

## 1. 聊天：一次只交一件事

最基础的用法就是对话。它适合问概念、改一句文案、把一段报错翻译成人话。

一次只交一件事。把这三样放进同一条消息里，比连着追问十轮有用：

- 你在哪：文件路径、命令、报错原文
- 你要什么：改完应是什么样
- 不要什么：这次别动的文件或别做的事

「帮我看看」通常得到一段泛泛的建议。「`src/config/siteConfig.ts` 里的站点描述太像主题默认文案，改成硬件工程师的个人介绍，别改别的字段」才会落到你要的那一行。

聊天的边界也很清楚：它看不见你的仓库。你贴多少，它就知道多少。过了这个边界，就该换下一种用法。

## 2. 进到项目里

写代码、改博客配置、对一整篇文章做结构，不要再把文件贴进网页。用能读仓库的工具，我这边是 Claude Code 和 Cursor。它们直接打开项目，改文件，跑命令，你看 diff 再决定留不留。

和聊天的差别只有一句：上下文从「你复制的片段」变成「仓库里真实的文件」。所以要说清范围，例如「只改这篇的 frontmatter，不要动主题」。

安装和账号见 [Claude Code](/posts/ai/vibe%20coding/Claude%20Code/)。本机小模型我用来补全或离线试一句，不拿它改整站，笔记在 [ollama](/posts/ai/ollama/)。

## 3. 把习惯写成规则

同一件事说了三遍，就不要再靠每次提醒。仓库根上的 `CLAUDE.md`、`AGENTS.md` 是给 AI 的站规：怎么构建、用什么包管理器、哪些目录不要动、提交信息用什么格式。

规则要短，而且一直生效。适合放进去的是「这个仓库永远这样」：

- 用 pnpm，不要用 npm 装依赖
- 不改上游主题源码，除非这是主题本身的问题
- 文章草稿和密钥不要提交

不适合放进去的是一次性任务：「今天把这篇封面换掉」。那是对话，不是站规。站规写长了，模型会跳着读，短约束反而更常被遵守。

## 4. 技能：一套可复用的步骤

规则回答「在这个仓库里什么永远不许做」。技能回答「遇到这类任务，按哪几步做」。

一份技能就是一个目录加一份 `SKILL.md`。里面写清：什么时候用、先读什么、做完要检查什么。它不是每句话都塞进上下文，而是这类任务出现时才被读到。例如「按本站文风写一篇博客」「发版前对一下评论和 RSS」。

和规则的差别：

| | 规则 | 技能 |
|---|---|---|
| 何时生效 | 打开这个仓库就在 | 任务对上了才读 |
| 写什么 | 约束，短 | 步骤，可稍长 |
| 例子 | 不要提交密钥 | 写文章：先看同系列旧文，再落盘，不顺便改主题 |

技能值得写的前提是你会再做第三次。第一次先在对话里做完。第二次还记得步骤，就先别抽象。第三次仍然手写同样的说明，再收成 `SKILL.md`。

OpenClaw 这边的技能是同一件事的另一个入口：代理自己去跑，缺技能时用 ClawHub 检索安装。安装向导里那几步我写在 [openclaw](/posts/ai/openclaw/openclaw.md)，这里不重复。飞书、QQ 那些通道笔记也在同一系列里。

## 5. 什么时候停

能用一句话讲清的，留在聊天里。要改仓库的，交给能读文件的工具，并看 diff。会在这个仓库里反复碰到的约束，写成规则。会在多篇文章或多台机器上重复的流程，写成技能。

不要为了显得高级，把每件事都做成代理或技能。技能多了和站规写太长是同一个问题：真正要遵守的那几条被淹没。我现在的分法就是上面这四层，工具笔记继续单独放着，这篇只负责说明哪一层该用哪一种。
